# DataPOS — အကောင့် လုံခြုံရေး ပြုပြင်ချက် (2026-09-19)

**ပြဿနာ (တိုင်းတာပြီး):** `/register` သည် ဖုန်းနံပါတ်ဖြင့် အကောင့်ရှိပြီးသားဖြစ်လျှင်
ထိုအကောင့်၏ **အမည်နှင့် စကားဝှက်ကို အစားထိုး** ခဲ့သည် (staff/manager/owner မှလွဲ၍)။
ဆိုလိုသည်မှာ **ဖုန်းနံပါတ်သိရုံဖြင့် မည်သူမဆို ဖောက်သည်အကောင့်ကို လွှဲယူနိုင်သည်**။
စမ်းသပ်တိုင်းတာချက် (ပြင်မီ):

```
PROBE claimed=same-record name=Attacker victim_password_still_valid=NO attacker_password_valid=YES
```

ထို့ပြင် `AccountController::orders` သည် "မိမိဖုန်းနံပါတ်ဖြင့် မှာထားသည့် အော်ဒါအားလုံး" ကို
အလိုအလျောက် ချိတ်ခဲ့သဖြင့် အကောင့်လွှဲယူသူသည် **ထိုဖုန်းနံပါတ်၏ အော်ဒါမှတ်တမ်း
(အမည်၊ လိပ်စာ၊ ဝယ်သည့်ပစ္စည်း)** ကိုပါ မြင်နိုင်ခဲ့သည်။

**အကြောင်းရင်း:** app တွင် ဖုန်းနံပါတ် **ပိုင်ဆိုင်ကြောင်း အတည်ပြုသည့် လမ်းကြောင်း မရှိ**
(SMS/Viber OTP မရှိ)။ ထို့ကြောင့် ဖုန်းနံပါတ်တစ်ခုတည်းဖြင့် အကောင့်ကို လွှဲပေးခြင်းသည်
ဘယ်တော့မှ မှန်ကန်မည် မဟုတ်ပါ။

---

## ပြုပြင်ချက်များ

### ၁။ အကောင့်တွင် စကားဝှက် **တကယ်ရှိပြီးသား** ဖြစ်လျှင် လွှဲယူခွင့် မပြု
- Migration `2026_09_19_000003` → `users.password_set_at` (nullable timestamp)။
  **NULL = POS ကောင်တာမှ ဖန်တီးထားသည့် အကောင့်** (random placeholder password)။
- Registration / staff reset လုပ်လျှင် `password_set_at` သတ်မှတ်သည်။
- `password_set_at` ရှိပြီးသားအကောင့်ကို ထပ်မှတ်ပုံတင်လျှင် **ငြင်း**သည် —
  "ဤဖုန်းနံပါတ်ဖြင့် အကောင့် ရှိပြီးဖြစ်သည်။ အကောင့်ဝင်ပါ…"။

### ၂။ ကောင်တာမှ ဖန်တီးသည့် အကောင့် — လွတ်နေလျှင်သာ လွှဲယူနိုင်
- အော်ဒါ သို့မဟုတ် Points/အသုံးစရိတ် တစ်ခုခု ရှိပြီးလျှင် **ဆိုင်မှ အတည်ပြုမှ လွှဲပေး**သည်
  (storefront မှ အလိုအလျောက် လွှဲလို့မရ)။
- လွတ်နေသေးသည့် အကောင့်ကို လွှဲယူလျှင် `audit_logs` တွင်
  `customer_account_claimed` ရေးသည် (ဘယ်သူ၊ ဘယ်ဖုန်း)။
- ဤနည်းဖြင့် "ကောင်တာတွင် ဖောက်သည်ထည့် → အွန်လိုင်းမှာ အကောင့်ဖွင့်" လမ်းကြောင်း
  မပျက်ဘဲ ဆက်အလုပ်လုပ်သည်။

### ၃။ staff/manager/**owner** အကောင့် လုံးဝ လွှဲယူလို့မရ
- ယခင် guard သည် `store_manager`,`staff` ကိုသာ စစ်သဖြင့် **`store_owner` လွတ်နေခဲ့သည်** —
  အော်ဒါမရှိသေးသည့် ဆိုင်ပိုင်ရှင်အကောင့်သည် လွှဲယူနိုင်ခဲ့သည်။ ယခု
  "retail/wholesale customer မဟုတ်သည့် membership ရှိသမျှ" ကို ငြင်းသည်။

### ၄။ အော်ဒါမှတ်တမ်း လွှဲယူခြင်း ကန့်သတ်
- `/account/orders` သည် ယခု **အကောင့်ဖန်တီးပြီးနောက်** တင်သည့် ဧည့်သည်အော်ဒါများကိုသာ
  ချိတ်သည် (အရင် မှာထားခဲ့သည့် မှတ်တမ်းများကို ဖုန်းနံပါတ်တူရုံဖြင့် မြင်လို့မရတော့)။
- မှတ်ချက်: မိမိအကောင့်မဖွင့်မီ မှာထားခဲ့သည့် အော်ဒါကို အကောင့်ထဲ ပြန်တွေ့လိုလျှင်
  confirmation လင့် (`/store/{slug}/orders/{id}/confirmation`) ဖြင့် ကြည့်နိုင်သည်။

### ၅။ ဆိုင်မှ စကားဝှက် ပြန်လည်သတ်မှတ်ခြင်း (recovery path)
- ဆိုင်သည် ဖုန်းနံပါတ်၏ ပိုင်ရှင်ကို ကိုယ်တိုင်သိသဖြင့် **ဆိုင်သာ** ပြန်လည်သတ်မှတ်နိုင်သည်။
- ဖောက်သည် directory (`/admin/customers`) တွင် ဖောက်သည်တစ်ဦးကို ပြင်ဆင်ရာ၌
  **"စကားဝှက် အသစ်"** အကွက် ထည့်ထားသည် (အနည်းဆုံး ၈ လုံး၊ ထည့်လျှင်သာ ပြောင်း)။
- `password_set_at` သတ်မှတ်ပြီး `audit_logs` တွင် `customer_password_reset` ရေးသည်။
- **မရှိသေးသည်:** ဖောက်သည် ကိုယ်တိုင် "စကားဝှက် မေ့သွားသည်" ဖြင့် ပြန်လည်သတ်မှတ်ခြင်း
  (အီးမေးလ်/SMS လိုသည်) — လက်ရှိတွင် ဆိုင်သို့ ဆက်သွယ်ရမည်။

## ကျန်ရှိနေသော အန္တရာယ် (ရိုးသားစွာ)

- ဤပြုပြင်ချက်သည် **ဖုန်းနံပါတ် အတည်ပြုခြင်း (OTP)** မရှိသည့် အခြေအနေအတွက်
  အန္တရာယ်ကို လျှော့ချခြင်းသာ ဖြစ်သည်။ **လွတ်နေသေးသည့် အကောင့်တစ်ခုကို
  ကြိုတင်လွှဲယူခြင်း** (ဖောက်သည်တစ်ဦး ကောင်တာတွင် အကောင့်ဖွင့်ထားပြီး အွန်လိုင်းမှာ
  မဝင်ရသေးခင် အခြားသူက လွှဲယူခြင်း) ဖြစ်နိုင်ဆဲဖြစ်သည်။
  ဖြေရှင်းရန် **SMS သို့မဟုတ် Viber OTP** လိုသည် (မြန်မာတွင် SMS တစ်စောင် ≈ ၁၅–၃၀ ကျပ်)။
- migration မတိုင်မီ ဖန်တီးထားသည့် အကောင့်များသည် `password_set_at = NULL` ဖြစ်သဖြင့်
  "မစစ်ဆေးရသေးသည့်" အကောင့်များ ဖြစ်သည် — အော်ဒါ/အမှတ် ရှိလျှင် ကာကွယ်ခံရသည်၊
  လွတ်နေလျှင် လွှဲယူနိုင်သည် (လိုအပ်လျှင် SQL ဖြင့် `password_set_at` ဖြည့်နိုင်သည်)။
